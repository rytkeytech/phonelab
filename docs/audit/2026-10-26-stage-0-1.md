## Stage 0: database hygiene

### Changes (not yet applied; see "Your steps")
- `supabase/migrations/0005_advisor_fixes.sql`
  - Rewrites the 4 public read policies without `is_staff()`. Every role sees the same rows as before.
  - `revoke execute on is_staff() from public, anon` and keep it for `authenticated`. Functions are executable by `PUBLIC` by default, so revoking from `anon` alone isn't enough.
  - Revokes execute on `rls_auto_enable()` from `public, anon, authenticated`, but only if the function exists. This doesn't stop a trigger or event trigger from running it.
  - Adds indexes on `game_results.scenario_id`, `repair_cases.reviewed_by`, `repair_media.uploaded_by` and `user_progress.lesson_id`.
- `scripts/db-check.ts`: new check: "anon can't execute any SECURITY DEFINER function".
- `scripts/db-snapshot.ts` + `npm run db:snapshot`: writes a read-only snapshot of the live schema (tables, indexes, policies, function definitions and grants, triggers, event triggers, table grants) to `supabase/snapshot/live-schema.md`. Commit it. Any later change made in the dashboard then shows up as a git diff. This stands in for `supabase db pull`, which needs the Supabase CLI and Docker.

### Not changed, on purpose
- **Overlapping permissive policies (13 warnings).** Merging "Anyone can read" with "Staff manage" into one policy per action would save a policy evaluation per row. The cost is policies that are harder to read and review. With tables this small, the speed gain can't be measured. Recommendation: leave as is until a table holds thousands of rows.
- **3 "unused index" notices** on `repair_cases`. They're unused only because there are no published cases yet. Keep them.

## Stage 1: accuracy audit

### What is in good shape
- Lessons give no board-specific voltages, pins or test points. The only numbers are Ohm's-law textbook examples (labelled "not a phone measurement"), the typical 32.768 kHz sleep clock, and a deliberately wrong quiz option ("Always 400 mV").
- Every scenario is labelled simulated, and the device says "Not a real model". Readings are described in words.
- All 8 sample repair cases are "Demo Phone A–H", flagged `isSample`, rated Hypothesis or Unverified, and carry a "Sample case: fictional device" notice.
- The Chipset Explorer is labelled conceptual, connections carry a disclaimer, and diagnosis steps defer to the schematic.

### Misleading or over-confident statements (fix in Stage 2)

| ID | Where | Statement | Problem | Proposed fix |
|---|---|---|---|---|
| A-01 | Scenario `dead-after-charge`, step `short`, choice `pmic-rails` | "PMIC rails aren't switched on before the power key is pressed, so they can't explain this current." | Overgeneralised. Many PMICs have always-on outputs (e.g. for the RTC), and a short on a PMIC input would also draw current. | "Most PMIC output rails are off before power-on, so the main supply line is the better first check. Some always-on outputs exist; the schematic shows which." |
| A-02 | Same scenario, steps `locate` and `conclude` | A hot spot on the charging IC leads straight to "The evidence chain is complete." | One hot spot rarely proves a cause. There's no confirmation step (e.g. the short clears with the part lifted), and "likely from the charger" treats correlation as cause. | Add a confirmation step before the conclusion. Reword the cause as "consistent with" the charger history. |
| A-03 | Scenario `logo-loop`, step `start`, choice `firmware` | Flashing firmware as the "best" first step. | No warning that flashing usually erases user data, and no step to get the customer's consent. | Add a data-loss caution and a consent step before flashing. |
| A-04 | Scenario `logo-loop`, step `evidence`, choice `battery` | "The phone powers up and starts booting every cycle, so the battery is supplying power. Nothing points at it." | A worn battery can sag under boot load and cause restarts. "Nothing points at it" is too strong. | Rate it "ok". Explain that running from a bench supply rules the battery out cheaply. |
| A-05 | Scenario `no-wifi`, step `supply`, choice `antenna`; debrief | "A greyed-out Wi-Fi switch usually means the Wi-Fi IC isn't starting." | Unsourced frequency claim. Firmware, driver or calibration-data problems can grey out the switch too. | "…suggests the Wi-Fi IC or its software isn't starting. Rule out software first, as you did." |
| A-06 | Scenario `no-wifi`, steps `clock` → `source` | The lesson teaches "power, clock and reset, in order", but the scenario never checks reset. The conclusion has no confirmation (clock restored after replacement). | Teaches skipping a step, and accepts a cause on a visible crack alone. | Add a reset check, or say why it's skipped. Add post-repair "clock now present" verification. |
| A-07 | Scenario `no-wifi` | `relatedLessonIds: []` | Missed link. | Link the new Clocks lessons. |
| A-08 | Lesson `fundamentals/diode-mode`, explorer link | "Most shorts you find this way are on PMIC output rails or the battery supply line." | Unsourced frequency claim. | "Supply lines, such as the main supply line and PMIC output rails, are where you'll use this most." |
| A-09 | Lesson `fundamentals/diode-mode` | "Diode mode is the most-used measurement in board repair." | Unsourced superlative. | "one of the most-used". |
| A-10 | Explorer block `pmic`, diagnosis | "A shorted capacitor or load on a rail is more common than a failed PMIC." | Unsourced frequency claim. Widely repeated by technicians, but repetition isn't evidence. | Tag as `engineering-inference` / Hypothesis, or reword as advice ("rule out shorted capacitors and loads before suspecting the PMIC"). |
| A-11 | Explorer block `storage` | "eMMC on many budget phones, UFS on most mid- and high-end phones." | Market generalisation with no source. | Needs a source or softer wording. Register question. |
| A-12 | Explorer block `soc` | Names "Qualcomm EDL" and "MediaTek BROM" modes. | Correct as far as I know, but no vendor source is cited. | Register question; cite vendor or reputable documentation. |
| A-13 | New Clocks lessons (uncommitted, written this session) | Probe capacitance can stop a crystal; crystals can be damaged by excess heat; some designs have no separate 32.768 kHz crystal; some PMICs need the sleep clock to finish power-on. | General principles from standard electronics knowledge. **No sources cited**, so they don't yet meet the new research rules. | Add `general-principle` citations (crystal / oscillator application notes) in Stage 2, or soften. |

### Structural gaps against the brief
- **No citation model.** Lessons, explorer blocks and scenarios have no `sources` field. Repair cases do have one (`SourceList`).
- **Confidence labels** exist for repair cases (`ConfidenceBadge`), but not for individual claims in lessons and explorer blocks.
- **Scenarios are linear**, 4–5 steps, one decision each. There are no branches, hints, back navigation, interpretation step, circuit view or final report. Scoring rewards choice quality only.
- **The Chipset Explorer has one conceptual mode** and no platform → chipset → model → board revision hierarchy. The `phone_models` table has `platform` and `chipset` as text columns only.
- **No research register** (`docs/research/` doesn't exist).
- **No automated tests.** There's no test runner in `package.json`; checks are lint, `tsc` and `next build`.
- **Learning progression:** topic 10 of the brief (display, touch, camera, audio, connectivity as subsystems) has no course. Today it's scattered across the "buses" course.
